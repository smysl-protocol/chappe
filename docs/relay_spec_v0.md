# Релей v0 — спецификация (только спека, кода нет)

Дата: 02.08.2026. Статус: черновик для обсуждения, сервер НЕ разворачивать.
Основа — фактический wire-формат на теге `codec-v2-pre-freeze`
(проверено по коду, не по памяти).

## Зачем релей

Оба собеседника редко в сети одновременно (LoRa-узел выключен, телефон
спит). Релей — почтовый ящик: принимает запечатанный конверт, держит до
появления получателя, отдаёт и забывает.

## Что релей ХРАНИТ

- **Шифротекст конверта как есть** — байты TEXT-пакета(ов) после
  заголовка: `[sentAtMinutes 4][0x03][eph_pub 32][nonce 12][ct][tag 16]`.
  Для релея это непрозрачный блоб.
- **Адрес ящика получателя** — отпечаток ключа получателя (8 симв.
  base32, как в Contact.id). Передаётся ОТДЕЛЬНЫМ полем обращения к
  релею (в самом конверте адресата нет — и не появится).
- **Время приёма** — для TTL.
- **msgID** (2 байта из заголовка) — для дедупликации повторов.

## Что релей НЕ хранит

- открытый текст, ключи, имена;
- связку «кто отправил» (отпечаток отправителя лежит ВНУТРИ шифротекста
  и релею недоступен);
- историю выдач (отдал → удалил);
- журналы IP дольше, чем требует защита от флуда (см. открытые вопросы).

## Срок хранения

**48 часов** с момента приёма. По истечении — удаление без следа.
Продление недоступно: хочешь дольше — шли заново.

## Что релей ВИДИТ (и это метаданные, которые мы осознанно отдаём)

| Поле | Откуда | Зачем релею |
|---|---|---|
| версия+класс (байт 0 заголовка) | заголовок конверта | принимает только TEXT (0x3); SOS широковещательный и релею не адресуется |
| flags, msgID | заголовок | дедуп повторов, сборка фрагментов НЕ делается (см. ниже) |
| sentAtMinutes (4 Б) | плейнтекст-префикс TEXT v1 | ничего — игнорирует; факт видимости зафиксирован |
| ящик получателя | поле обращения | маршрутизация |
| размер блоба, время приёма, IP источника | транспорт | лимиты, TTL |

## Что релей НЕ ВИДИТ (непрозрачно по построению)

- содержимое (`ct` под ChaCha20-Poly1305);
- отправителя (его pubkey — внутри `ct`);
- тип содержимого (семантические коды / текст / позиция — кодек-байт
  внутри `ct`);
- связность диалога (нет счётчиков, тредов, ack-статусов).

Фрагментированное сообщение (флаг бит 0) релей хранит как НАБОР
пакетов одного msgID, не собирая: сборка — дело получателя.

## Формат обращения (транспорт — HTTPS, поверх него минимум)

```
PUT /box/{отпечаток}/msg        тело: байты пакета конверта
GET /box/{отпечаток}            → пакеты, старые первыми; после
                                  подтверждения (DELETE или ack-параметр)
                                  — удаление
DELETE /box/{отпечаток}/{msgID}
```

Аутентификация ящика при GET: подпись nonce-челленджа ключом,
отпечаток которого равен имени ящика (иначе любой, узнав отпечаток,
выкачает чужой шифротекст; расшифровать не сможет, но объём/время —
тоже данные). Точная схема — вопрос №2; **решён 04.08.2026: принят
суточный box-ключ без предъявления pubkey (вариант В), см. ниже.**

## Поведение при переполнении

Лимиты на ящик: **N сообщений / M килобайт** (дефолты — открытый
вопрос №3). При переполнении: новые сообщения **отвергаются с кодом
«ящик полон»** — отправитель получает честный отказ и решает сам
(повторить позже / отдать по LoRa). Старые НЕ вытесняются: тихая
потеря уже принятого хуже громкого отказа новому.

## Недоступность получателя

Получатель не появился за 48 ч → сообщение удаляется. Никаких
уведомлений отправителю (релей не знает, как его найти, и не должен).
Отправитель узнаёт о доставке единственным честным способом —
envelope-ack от самого получателя тем же каналом.

### Опорные определения (чтобы через месяц не расшифровывать)

- **Суточный псевдоним (dst)** — 8 байт
  `SHA-256(pubkey получателя ‖ unix-день LE)[0..8)`, код
  `MailboxID.dst` в `EnvelopeV2.swift`. Вращается по суткам; релей
  pubkey не знает и сутки связать не может (Дополнение 02.08 выше).
- **D** — в этом дополнении: полные 32 байта того же хеша
  `SHA-256(pubkey ‖ unix-день LE)`. dst — его первые 8 байт; байты
  `D[8..32)` на провод не идут, но вычислимы каждым, кто знает pubkey
  получателя, — и никем больше. На этом строится вариант В вопроса №2.
- **Круг знающих pubkey** — сам получатель и все, кому он показал
  визитку (контакты). Любая способность, выводимая из pubkey,
  автоматически доступна всему кругу; это ограничение по построению,
  оно всплывает в №2 и №3 несколько раз.
- **XEd25519** — подпись X25519-ключом через отображение его в
  Ed25519 (схема Signal); упомянута в исходной формулировке №2.
- **Bearer-доступ** — доступ «по предъявлению знания»: знаешь
  секретное имя ящика (dst) — значит, имеешь право; криптопроверки
  нет.
- **Box-ключ** — предлагаемая в №2 (вариант В) детерминированная пара
  Ed25519 с сидом `HKDF(D, "mailbox-read")`: вычислима из pubkey
  получателя + номера суток, живёт одни сутки вместе с dst.
- **PoW (proof-of-work, hashcash)** — клиент прикладывает к запросу
  nonce, при котором хеш запроса имеет N ведущих нулевых бит:
  проверка дешёвая, подбор дорогой (батарея/время).
- **Токен знакомства** — секрет, который получатель выдавал бы
  контакту при обмене визитками для предъявления релею при отправке.
- **Федерация** — несколько независимых релеев; у получателя свой
  набор, отправитель должен знать, куда класть.

### Методика счёта (все числа воспроизводимы из этих формул)

- Кадр v2 session через релей = заголовок 4 + dst 8 +
  `[4][тег 4][счётчик 2]` 7 + шифртекст (минуты 4 + внутр. кодек 1 +
  смысл) + AEAD 16. Проверка против `RM_Envelope_v2_draft.md`
  сошлась: «ок» (4 Б смысла) = 44 Б, отель (35 Б) = 75 Б.
- Ёмкость ящика: активный диалог ~100 входящих/сутки × 48 ч хранения
  × ~75 Б ≈ 200 кадров ≈ 15 КБ. Максимальное фрагментированное
  сообщение = 16 фрагментов × 200 Б = 3,2 КБ
  (`Envelope.maxFragments`, `Envelope.maxPayload`).
- Оценки одноразово пересчитаны скриптом вне репозитория; в git
  остаётся только методика (эти формулы).

### №2. Аутентификация GET — ПРИНЯТО владельцем 04.08: суточный box-ключ (В)

Сдвиг постановки против 02.08: вопрос писался, когда именем ящика был
статический отпечаток из визитки — публичный по сути. Теперь имя
ящика — суточный псевдоним: «узнать» его нельзя, можно только
вычислить из pubkey. Угроза «любой, узнав отпечаток, выкачает»
сузилась до двух групп: (1) круг знающих pubkey; (2) увидевшие dst
постфактум — журналы/диск релея, чужой релей при будущей федерации,
компрометация TLS-терминатора.

**Вариант А — подпись identity-ключом с раскрытием pubkey.**
GET несёт pubkey получателя и подпись челленджа (XEd25519 от identity
X25519 либо отдельный Ed25519 из сида личности); релей проверяет
подпись и равенство `SHA-256(pubkey ‖ день)[0..8) = имя ящика`.
- Цена: кадр LoRa — 0 Б (всё в HTTPS-обращении); запрос +32 Б ключ,
  +64 Б подпись, +1 RTT челленджа; хранения у релея нет.
- Что ломается: релей узнаёт pubkey → вычисляет dst этого получателя
  на ЛЮБЫЕ сутки, прошлые и будущие → суточная ротация псевдонимов
  обнуляется, межсуточная несвязываемость (Дополнение 02.08)
  уничтожается. Релей также получает сам pubkey — материал, которого
  по разделу «Что релей НЕ хранит» у него быть не должно.
- Единственный вариант, защищающий ящик и ОТ КОНТАКТОВ (у них нет
  приватного ключа). Это его единственное преимущество перед В.
- **Отклонён владельцем 04.08** (предъявление pubkey релею обнуляет
  суточные псевдонимы).

**Вариант Б — bearer: GET без аутентификации.**
- Цена: ноль всего.
- Что ломается: читать И УДАЛЯТЬ (DELETE/ack) ящик может любой из
  круга pubkey и любой увидевший dst в журналах/на диске релея.
  Чужое удаление = тихая невосполнимая потеря почты (отправитель
  считает «лежит в ящике»). Объём и времена сообщений — тоже данные.
- **Отклонён владельцем 04.08** (неавторизованный DELETE = тихая
  потеря почты).

**Вариант В — суточный box-ключ из свободных байт D.**
Сид ключа ящика = `HKDF(D, "mailbox-read")` → детерминированная пара
Ed25519. Проверочный ключ (32 Б) регистрируется ПЕРВЫМ PUT в ящик
(его знает и отправитель — он тоже выводит D из pubkey); PUT без
ключа в новый ящик отвергается. GET и DELETE — подпись челленджа
релея box-ключом.
- Цена: кадр LoRa — 0 Б; +32 Б к первому PUT суток; GET/DELETE:
  челлендж 16 Б + подпись 64 Б + 1 RTT; хранение релея +32 Б/ящик;
  сложность — HKDF и Ed25519 из детерминированного сида, стандартные
  примитивы CryptoKit.
- Что сохраняет: релей pubkey не видит, межсуточная несвязываемость
  не трогается; «увидел dst в логах» больше не даёт ни чтения, ни
  удаления.
- Что остаётся (принятая утечка): круг знающих pubkey может вычислить
  box-ключ → читать и удалять ящик контакта. Отделить получателя от
  его контактов, не предъявляя релею identity-ключ, невозможно по
  построению — в этом и состоит выбор между В и А. При парке из двух
  своих телефонов допущение «контакты не злоупотребляют» тривиально
  истинно; при росте — фиксируется в списке принятых утечек.
- Новых допущений доверия К РЕЛЕЮ не появляется.

**РЕШЕНИЕ ВЛАДЕЛЬЦА 04.08.2026 (была рекомендация В — принята):**
суточный box-ключ без предъявления pubkey — вариант В. Варианты А и
Б — **отклонены владельцем 04.08**: А обнуляет суточные псевдонимы
ради защиты от контактов, которая на текущем парке не нужна; Б —
из-за неавторизованного DELETE (тихая потеря почты). Запасная
ступень из прежней рекомендации («GET по bearer, DELETE с подписью»)
решением не задействована — принят полный вариант В; как живой
вариант она больше не рассматривается.

### №3. Лимиты ящика и флуд — РЕШАЕМО СЕЙЧАС (дефолты, IP-лимиты); PoW внутри вопроса — отложен

Вопрос распадается на ДВЕ разные угрозы с разными защитами.

**Угроза 1 — мусор в ящик конкретной жертвы**: залить ящик до лимита,
и «честный отказ» из раздела о переполнении обернётся против нас —
релей будет отказывать настоящим отправителям (DoS адресата).
- Закрывается распространением варианта В (№2) на запись: PUT в
  существующий ящик подписывается тем же box-ключом. Чужак без
  pubkey не вычислит D → писать в ящик жертвы не может. Цена: +64 Б
  на PUT. Круг pubkey писать может — он и должен: это отправители.

**Угроза 2 — диск и полоса релея целиком.** Атакующему не нужен чужой
ящик: имя ящика — любые 8 байт, релей по построению не отличает
настоящий dst от случайного (pubkey он не знает) и создаёт ящик на
первый PUT. Per-box криптография здесь бессильна; работают только
ресурсные лимиты.

Варианты по угрозе 2:

- **(а) IP-лимиты + глобальная квота.** Дефолты-предложение (всё —
  конфиг релея, формат провода не трогается): ≤120 PUT/час с одного
  IP (burst 30); тело PUT ≤ 256 Б (кадр не бывает длиннее
  `maxPayload` ≈ 200 Б, запас на будущее); глобальная квота диска
  (например 4 ГБ ≈ 64 тыс. полных ящиков), при 80 % — ужесточение
  per-IP и per-box лимитов, при 100 % — отказ «релей полон». Журнал
  IP — скользящее окно 1 час, дальше стирается (согласовано с «Что
  релей НЕ хранит»). Что ломается: VPN/ботнет обходит per-IP;
  целевой DoS квоты остаётся возможным — но становится видимым в
  журнале отказов.
- **(б) PoW (hashcash)** на PUT, ~20 бит (≈1 с подбора). Асимметрия
  ПРОТИВ нас: платит честный телефон в поле батареей, ботнету с GPU —
  копейки. Вводить по теории — плата без данных.
- **(в) Токен знакомства.** Релей не может проверить токен, не зная
  секрета получателя; проверяемым токен становится только через
  реестр «ящик → токен» у релея, а стабильный реестр — это ровно та
  связываемость, против которой строились суточные псевдонимы. Всё,
  что даёт токен, box-ключ (угроза 1) даёт дешевле и без реестра.

**Дефолты лимитов ящика** (методика выше): **N = 256 пакетов,
M = 64 КБ** на ящик-псевдоним. Обоснование: 48 ч активного диалога ≈
200 кадров / ≈15 КБ → запас ×4 по байтам и ×1,3 по пакетам; 64 КБ
вмещают 20 максимальных фрагментированных сообщений по 3,2 КБ.

**РЕКОМЕНДАЦИЯ (решение — владельца):** принять сейчас дефолты
N=256/M=64 КБ, вариант (а) и подпись PUT box-ключом (№2 В). Токен
знакомства (в) — отклонить (непроверяем без реестра; реестр =
связываемость; дублирует box-ключ). **PoW (б) — отложен, потому что**
нет полевого сигнала злоупотребления: релей не развёрнут, парк — два
своих телефона, а цена — батарея честных узлов. Откроется, когда релей
станет публичным (чужие клиенты) И журнал отказов покажет флуд,
который не гасится вариантом (а). Задел, чтобы включение не ломало
клиентов: в формате PUT заранее предусмотреть опциональное поле
`pow` — зарезервировать имя поля сейчас, семантика при включении.

### №4. Федерация — РЕШАЕМО СЕЙЧАС для v1; протокол мультидоставки — отложен

Констатация: формата визитки в репозитории ещё НЕТ (проверено по
docs/) — «список в визитке» сегодня означает требование к её будущему
проектированию, а не правку существующего артефакта.

- **(а) Один релей, адрес в конфиге приложения.** Цена: 0 Б в
  визитке, одна точка доставки, минимальный клиент. Что ломается:
  единая точка отказа (релей упал — вся релейная доставка лежит;
  радио остаётся) и единая точка наблюдения метаданных (все ящики,
  размеры, тайминги — у одного оператора). Пока оператор релея =
  владелец, а парк = два телефона, наблюдатель совпадает с
  наблюдаемым — приемлемо.
- **(б) «Домашний релей» в визитке** (одна запись, как хост в
  email-адресе). Цена: ~25–40 Б в визитке/QR. Что ломается: смена
  релея = переиздание визитки, а канала обновления визиток нет →
  все, у кого старая визитка, теряют релейную доставку до новой
  личной встречи.
- **(в) Список релеев в визитке**, слать во все (или в первый
  живой). Цена: ~25–40 Б × N в QR; при «во все» — трафик и хранение
  ×N. Дубли между релеями получатель гасит УЖЕ существующими
  механизмами: дедуп (сессия, счётчик) до расшифровки (`Ratchet`,
  черновик v2) и msgID. Что ломается: сложность клиента (обход
  списка, частичные отказы); каждый релей списка всё равно видит
  свою копию метаданных — утечка не убывает, только точка отказа.

**РЕКОМЕНДАЦИЯ (решение — владельца):** для v1 — вариант (а). При
проектировании формата визитки сразу заложить **поле-список
`relays`** с потолком (правило CLAUDE.md «у каждого повторяемого поля
есть потолок»; предлагаю maxItems=3): поле с одной записью ведёт себя
как (б), рост до (в) не меняет формата визитки. **Протокол
мультидоставки (обход списка, ретраи, частичные отказы) — отложен,
потому что** нет второго физического релея, нет формата визитки и нет
полевых данных о недоступности единственного. Откроется при любом из
событий: появился второй релей; визитка пошла в проектирование (тогда
из этого вопроса берётся только резерв поля `relays`). Пересечение с
ролью раздатчика таблиц (`relay_spec.md` §8.5): каждый релей списка
может, но не обязан, совмещать роли; схождение версий таблиц ведёт
WP0 — здесь не дублируется.
