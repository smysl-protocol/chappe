# R+M — Менеджер доставки: приоритет каналов (интернет / LoRa)

**Статус:** проектное решение (каркас v0)
**Дата:** 26 июля 2026
**Связано:** docs/RM_Envelope_v0.md (конверт), docs/semantic_compression.md (кодек), docs/sophie_presence.md (Кая — не участвует)

---

## 0. Принцип

Envelope — транспорт-агностик: конверт один, носителей много. Добавление
интернет-доставки (WiFi / сотовая) не меняет формат пакета, словарь и кодек —
меняется только то, **чем** конверт везём. Всё новое живёт в одном модуле —
**менеджере доставки** — под очередью envelope.

```
сообщение → конвейер (пивот→коды) → envelope
                                       ↓
                              МЕНЕДЖЕР ДОСТАВКИ
                          (выбор канала, повторы, статусы)
                        ↙            ↓            ↘
                    WiFi          сотовая         LoRa
```

## 1. Режимы (выбор пользователя)

| Режим | Логика | Зачем |
|---|---|---|
| **Авто** (по умолчанию) | получатель доступен по интернету → IP; иначе → LoRa | просто работает |
| **Только LoRa** | интернет-стек не трогается вообще | радио-независимость / приватность одним тапом («авиарежим наоборот») |
| **Только интернет** | LoRa молчит | экономия эфира/батареи там, где связь есть |

Правила Авто: WiFi предпочтительнее сотовой; при неудаче доставки по IP —
автоматический откат на LoRa; envelope одинаков в обоих путях.

**Лимит полезной нагрузки — ПАРАМЕТР пути отправки, не константа.**
Менеджер доставки обязан передавать кодеку/фрагментатору лимит
выбранного канала: Envelope.maxPayload для LoRa, для IP-пути — без
обрезания. Правило П5 (обрезание хвоста SOS) применяется только
к лимиту фактического носителя; по IP SOS не обрезается никогда.

## 2. Lossless-дополнение по жирному каналу

По IP канал не ограничен лимитом MAX_PAYLOAD (источник истины —
Envelope.maxPayload в коде, сейчас 200 Б, уточняется на железе) → шлём **тот же envelope + оригинальный
текст** как дополнение. Получатель с интернетом видит идеальный текст;
получатель на LoRa — разворот кодов Smysl. Единый источник правды — коды;
текст — необязательный бонус. (Открытый вопрос: слать текст всегда или по
запросу — трафик/батарея.)

## 3. Мосты и гибридный меш

Интернет-путь требует точки встречи: **(а)** свой релей-сервер (E2E-шифрование
envelope сохраняется, релей видит только шифроблоб), или **(б)** узлы-мосты:
устройство с интернетом ретранслирует envelope между LoRa-облаками (паттерн
MQTT-моста Meshtastic). Вариант (б) идеологически наш: интернет — ещё один хоп
меша, а не замена. **Решение по мосту — отдельный док, здесь не принимается.**

## 4. Размещение в интерфейсе

1. **Настройки → «Доставка»**: режим (Авто / Только LoRa / Только интернет),
   в Авто — переключатели «использовать WiFi» / «использовать сотовую».
2. **Быстрый переключатель**: чип текущего режима над списком чатов или в
   шторке; тап — смена режима без похода в настройки.
3. **Значок канала на сообщении**: каждое отправленное несёт иконку пути
   (wifi / сота / радио) в статусе доставки; при откате Авто→LoRa значок
   меняется. Состояния: отправлено (канал) → доставлено → ретранслировано N.
4. Per-chat override («этому контакту — только LoRa») — кандидат на v2,
   сейчас не делаем.

## 5. Что не затрагивается

- Envelope, словарь, кодек, SOS-конвейер — без изменений.
- **Кая**: полностью локальна, менеджер доставки её не касается ни в одном
  режиме; шёпот по-прежнему ноль байт куда-либо.
- Планировщик модели — без изменений (доставка не использует LLM).

## 6. Открытые вопросы

1. Мост: свой релей vs узлы-мосты vs оба (отдельный док).
2. Обнаружение «получатель доступен по IP» без утечки присутствия.
3. Политика lossless-дополнения (всегда / по запросу / по WiFi-only).
4. Шифрование: единая E2E-схема поверх обоих путей (envelope уже шифроблоб —
   подтвердить, что IP-путь ничего не добавляет открытым).

### Замечания сверки §5 с реальным кодом (26.07.2026)

Проверено: `sim/envelope.py`, `sim/transport_sim.py`, `ios/RM/RM/Envelope/`.

5. **Число «190 байт» в §2 расходится с кодом и спекой.** В обеих
   реализациях лимит — `MAX_PAYLOAD = 200` / `Envelope.maxPayload = 200`;
   спека §9 говорит «~200, уточнить на железе». Цифру 190 в этом доке
   привести к единому источнику (константа конверта), чтобы не жило
   два разных лимита. **Решено, канон — символ в коде** (Envelope.maxPayload;
   упоминания в доках заменены 26.07.2026).
6. **Транспорт-агностичность подтверждается.** Лимит параметризован:
   `encode(max_payload:)` и `encode_text(max_payload:)` принимают его
   аргументом в обеих реализациях; тайминги и потери существуют только
   в симуляторе канала (уровень носителя); выше конверта захардкоженных
   LoRa-допущений не найдено. Одно допущение живёт ВНУТРИ конверта
   осознанно: правило П5 (SOS в один пакет — отрезание хвоста) считается
   от лимита носителя. Следствие для менеджера доставки: он обязан
   передавать кодеку лимит ВЫБРАННОГО канала (для IP-пути лимита нет —
   хвост SOS не режется), иначе IP-доставка унаследует LoRa-обрезание.
   **Решено, внесено в §1** (жёсткое требование «лимит — параметр пути»).
7. **«Кая — ноль байт куда-либо» — верно с dev-оговоркой** из
   sophie_presence.md §3: при remote-профиле (llama-server на Маке) шёпот
   физически идёт по Wi-Fi; в пользовательской сборке гейтится
   локальным провайдером.
8. **«Планировщик модели — без изменений»** — уточнение: планировщика
   в коде пока нет вообще (фаза 1 описана в sophie_presence.md §5);
   независимость доставки от LLM подтверждается — в модулях Envelope
   и симулятора нет ни одного обращения к LLM-слою.

   (синий зарезервирован за ассистентом).
