# Софи как ассистент приложения — спецификация

Версия: 0.2
Дата: 05.08.2026
Заменяет: 0.1 (черновик от 05.08)

---

## 0. Одной фразой

Софи — голос и маршрутизатор поверх детерминированной системы. Все
факты даёт код, все действия исполняет код, все решения «пора
заговорить» принимают правила. Модель формулирует и понимает —
больше ничего.

**Проверка конструкции:** при выключенной модели вся подсистема
обязана работать, теряя только естественный язык. Плейбуки
показываются карточками, диагностика считается, состояние видно.
Если что-то ломается без модели — это спроектировано неверно.

**Второе следствие, важнее первого:** каждый раз, когда Софи что-то
знает сама, а не из снимка или пака, — это будущий баг. Она хорошая
хозяйка ровно в той мере, в какой не является источником фактов.

---

## 1. Принципы

**П1. Факты — от кода.** Софи не «смотрит экран» и не выводит
состояние из диалога. Есть единственный источник — снимок состояния.
Модель читает его как данные.

**П2. Действия — через закрытый enum.** Модель возвращает структуру,
не текст с командами. Невалидный интент отбрасывается, пользователь
получает переспрос.

**П3. Интент прослеживается, как сущность в пивоте.** Аргументы
интента должны опираться на спаны исходной реплики. Отрицания
проверяются отдельно, до исполнения. Основание: классификация
интента — та же задача, что выбор смысла, и с той же поломкой.
Опасен не низкоуверенный ответ, а высокоуверенный неправильный.

**П4. Инициатива — от правил.** Модель никогда не решает, что пора
вмешаться.

**П5. Обратимость определяет тип подтверждения.** Показать — без
спроса. Обратимое — кнопка в чате. Значимое — отдельный экран.

**П6. Всё видно.** Каждое действие Софи — строка в журнале,
доступном пользователю.

**П7. Ничего не запоминается за пределами диалога.** «Еду в море»
живёт в текущей сессии. Профиля интересов нет.

---

## 2. Контракт незнания — пишется первым

Софи отвечает из трёх источников: снимок состояния, паки знаний,
реестр интентов. Маршрутизация между ними должна быть строгой, а
поведение при промахе — единым.

**Правило:** не нашлось ни в снимке, ни в паках, ни в enum — честный
отказ. Не «вероятно», не «обычно бывает так», не ответ из общих
знаний модели.

Основание — два зафиксированных провала:

- вопрос о происхождении названия: ретривер не нашёл, модель выдала
  «старинные шапки», сообщив при этом, что в базе объяснения нет;
- вопрос о годе: модель выдала «официально в 1844 году» — года,
  которого нет ни в одном паке.

Оба раза механика одинаковая: промах → ответ из весов.

### Поведение вне зоны

Отдельно описать и протестировать реакцию на то, что спросят в
первый же день:

| Запрос | Ответ |
|---|---|
| новости, курсы | Не знаю, у меня нет доступа к сети |
| Медицина за пределами пака | Отсылка к паку первой помощи, дальше — нет |
| «Напиши за меня сообщение» | Могу предложить формулировку, отправишь сам |
| «Что мне ответить NN» | Отказ: чужую переписку не читаю |
| Общие знания (столица, история) | Не моя зона, у меня только паки и состояние |
Погода — исключение, и оно скоро станет реальным. Планируется
офлайновый погодный слой (сжатые тайлы прогноза, приходят по
каналу связи). Когда он появится, погода станет ЧЕТВЁРТЫМ
источником фактов наравне со снимком, паками и интентами — со
всеми теми же правилами: данные от кода, честное «нет данных
на этот район», указание давности прогноза.

До появления слоя — честное «пока не умею».
Формулировки отказа — часть тона (см. §9), но факт отказа
детерминирован и не зависит от модели.

### Красные фикстуры

Все случаи выше + оба зафиксированных провала — в набор, который
обязан гореть до реализации контракта и оставаться зелёным после.

## 3. Снимок состояния

Единый объект, собираемый кодом по запросу.

```
snapshot {
  time, appVersion, locale

  radio {
    linkState: connected | connecting | disconnected | absent
    deviceName, lastPacketAgo, rssi, snr
    region, spreadingFactor
    batteryPercent
    heartbeatAgo
  }

  relay {
    reachable, lastSuccessAgo, endpoint
    networkPath: wifi | cellular | none
  }

  model {
    id, version, quantization
    loaded, roles, lastTokensPerSecond
    harnessResult: passed | degraded | unknown
    queueDepth            // добавлено в 0.2
  }

  storage {
    freeBytes, appTotalBytes
    byCategory: { packs, maps, history, modelWeights, cache }
  }

  packs [ { id, version, sizeBytes, installedAt,
            lastUsedAt, hitCount } ]

  maps  [ { regionId, sizeBytes, installedAt, lastUsedAt } ]

  messaging {
    outboxDepth, lastSendResult
    fallbackCount24h, semanticCount24h
    failedSends1h
  }

  security { unverifiedContacts, keyChangeAlerts }
}
```

Правила снимка:

- Ни одного поля, вычисляемого моделью.
- `lastPacketAgo` и `heartbeatAgo` — разные вещи. Первое: когда
  пришли данные. Второе: когда наблюдатель подтвердил, что жив.
  Молчание без пульса — отказ, а не тишина.
- В промпт идёт срез под текущий домен, не весь объект.
- Поля `updateAvailable` в 0.2 нет: каталога в v1 нет (§8).

## 4. Реестр интентов

### Класс A — показать, без подтверждения

| Интент | Аргументы |
|---|---|
| `explain_state` | `domain` |
| `show_diagnostics` | — |
| `show_storage` | — |
| `list_packs` | `filter` |
| `show_journal` | — |

**`open_screen` переведён в класс B.** Навигация посреди набора
сообщения теряет черновик — это не «показать».

### Класс B — обратимое, кнопка в чате

| Интент | Аргументы |
|---|---|
| `open_screen` | `target` |
| `pack_remove` | `packId` |
| `map_remove` | `regionId` |
| `radio_reconnect` | — |
| `radio_forget_pair` | — |
| `playbook_start` | `playbookId` |
| `playbook_step_done` | `stepId` |

Оговорка по «обратимости»: `pack_remove` на большом паке без сети
обратим только теоретически, `radio_forget_pair` требует
пересопряжения по коду. Кнопка должна честно говорить цену:
«удалить 180 МБ, скачать обратно можно будет при сети».

### Класс C — значимое, отдельный экран

| Интент | Почему C |
|---|---|
| `radio_set_region` | законность излучения |
| `history_delete` | необратимо |
| `contact_verify_start` | безопасность |
| `keys_reset` | необратимо |

**`model_switch` убран.** Цифры кодека привязаны к паре «протокол +
модель»; смена модели пользователем даёт поток несравнимых отчётов
и подрывает дисциплину заморозки. Одна модель в v1.

### Чего в enum нет и не будет

- Отправка сообщений от имени пользователя.
- Чтение содержимого чужих чатов, но те в которые ее вызвали через @ может читать и давать советы оставаясь невидимой для другой стороны.
- Изменение настроек приватности.
- Открытие системных настроек iOS — технически невозможно
  (`App-Prefs:` приватная схема). Остаётся текст + кнопка «сделал».
- Софи видит только тот чат, из которого её вызвали, и только
  пока вызвана. Позвал в один чат — про другие не знает и
  спрашивать бесполезно.
- Содержимое чата живёт в сессии и не переживает выход из неё.
  Ни в журнал, ни в кэш промптов, ни в дневник оно не попадает —
  проверить замком.

§2, строка таблицы:
«Что мне ответить NN» → в чате, где ты есть — помогу
сформулировать; про чужие чаты — не знаю.

### Контракт ответа модели

```json
{
  "intent": "<enum>",
  "args": { },
  "spans": [ { "arg": "packId", "start": 12, "end": 24 } ],
  "text": "<реплика>",
  "confidence": "high" | "low"
}
```

`spans` добавлены в 0.2 и обязательны: аргумент без привязки к
исходной реплике не исполняется. Constrained decoding по грамматике.

**Проверка отрицаний перед исполнением.** Реплика «не удаляй пак с
картами» не должна давать `pack_remove`. Использовать тот же
механизм, что в гейте отрицаний кодека, а не отдельную эвристику.

## 5. Распознавание без модели

Класс A распознаётся **детерминированным сопоставлением**, без
обращения к LLM. «Покажи диагностику», «сколько места», «что с
сетью» — конечный список формулировок.

Причины:

- пивот занимает ~4,4 с на телефоне; ждать столько ради «покажи
  память» неприемлемо;
- эти интенты нужны как раз тогда, когда что-то сломалось — в том
  числе сама модель.

Модель подключается только там, где нужно понять свободную речь.

---

## 6. Очередь к модели

Модель одна, претендентов четыре: пивот сообщений, чат Софи,
структурная экстракция, маршрутизация интентов.

Требуется явная политика:

- приоритет: отправка сообщения выше, чем реплика Софи;
- `queueDepth` в снимке — чтобы Софи могла честно сказать «сейчас
  занята отправкой»;
- пользователь видит ожидание, а не молчание;
- при `harnessResult: degraded` роутер не используется вообще,
  работает только детерминированный класс A.

Последнее — прямое применение правила о пульсе: деградировавшая
модель не должна выглядеть как работающая.

## 7. Плейбуки

Декларативное дерево. Работает без модели — шаги показываются
карточками. С моделью она озвучивает шаг, не меняя порядок.

**Шаг закрывается проверкой снимка, а не словом пользователя.**
«Сделал» — ускоритель, не условие.

### `radio_recovery`

Порядок от дешёвого к дорогому. Тумблер Bluetooth не первый — он
роняет весь стек.

1. `radio_reconnect` внутри приложения. verify: `linkState ==
   connected`.
2. Проверить, что устройство включено и рядом.
3. `radio_forget_pair` → экран выбора устройства.
4. Внешний шаг: Bluetooth в настройках выключить на 15 с. Текст +
   кнопка «сделал», verify по снимку.
5. Перезагрузить устройство физически.
6. Тупик: собрать отчёт, предложить показать целиком.

**Отдельная ветка:** если на телефоне установлено официальное
приложение Meshtastic — это самая частая причина. Очередь узла одна
и глобальная, кто первый прочитал, того и пакет. Проверить и сказать
об этом первым, до всех остальных шагов.

### `storage_cleanup`

1. Разбивка по категориям.
2. Кандидаты: паки с `hitCount == 0` или `lastUsedAt` старше 90
   дней; карты давно не открывавшихся регионов.
3. Подтверждение по каждому, освобождаемый объём считает код.
4. Веса модели — последними, с отдельным предупреждением.

### `first_run`

Переписан относительно 0.1. Приложение работает через интернет;
радиоустройство — дополнительная возможность, а не условие.

1. Объяснить, что уже работает.
2. Довести до первой сверки контакта — это главный шаг, без него
  переписка не защищена от подмены.
3. Радио упомянуть как «если у вас есть устройство».

### `explain_delivery`

Не плейбук, а частый вопрос «почему долго идёт». Ответ строго из
снимка: каким путём ушло, режим, глубина очереди, ужалось ли
смыслом, что означает статус.

## 8. Чего в v1 нет

Вынесено сознательно, с основанием.

**Каталог и загрузчик** (паки, карты, модели одним механизмом).
Подписанные манифесты, возобновляемая загрузка, атомарная установка,
откат, проверка целостности — отдельный проект того же размера, что
раздача table-pack, которая сама ещё не обкатана. В v1 паки вшиты в
сборку.

**Движок правил и проактивность.** Пороги калибруются на живом
использовании, которого нет. Софи, заговорившая не вовремя,
раздражает сильнее молчащей. Первые пользователи дадут материал.

**Смена модели пользователем.** См. §4.

**Подбор паков по контексту разговора.** Даже по запросу — сначала
нужен каталог. Плюс это единственное место, где Софи спрашивала бы о
планах пользователя; вводить его стоит осознанно, не походя.

## 9. Решить до первой строки UI

**1. Вокабуляр — задача номер ноль.** Правило запрещает «узел»,
«LoRa», «mesh», «LLM» в пользовательских строках. Вся эта спека
написана внутренними терминами. Нужен словарь замен: как называется
спаренное радиоустройство, радиоканал, сама модель, семантическое
сжатие. От него зависят тексты плейбуков, названия в журнале и
формулировки отказов — переписывать дважды дорого.

**2. Тон Софи.** Диапазон от сухого инструктора до собеседника —
разные тексты. Выбрать до написания плейбуков.

**3. Уведомления.** Локальный пуш при закрытом приложении или только
карточка при открытом. Пуш «связь потеряна» ночью — плохой опыт.

**4. Журнал: срок хранения.** Бесконечный журнал — след поведения
пользователя на устройстве, читаемый при изъятии телефона. Тот же
класс, что история чатов, и защита нужна та же.

## 10. Границы

- Софи не читает переписку.
- Софи не отправляет сообщения и не отвечает за пользователя.
- Софи не трогает регион радио, ключи и приватность сама.
- Софи не выдумывает статус: нет поля в снимке — «не знаю».
- Тревоги безопасности идут мимо Софи. Смена ключа контакта —
  системное предупреждение, не реплика ассистента.

---

## 11. Порядок работ

1. **Словарь замен для UI.** Без него всё остальное придётся
   переписывать.
2. **Контракт незнания** (§2) для всех трёх путей + поведение вне
   зоны + красные фикстуры. Это уже дважды ломалось.
3. **Снимок состояния и пульс наблюдателя.** Нужен независимо от
   Софи — без него «тишина не есть отказ» не выполняется.
4. **Детерминированное распознавание класса A**, без модели.
5. **Реестр интентов, роутер, журнал** — с прослеживаемостью спанов
   и проверкой отрицаний.
6. **`radio_recovery` в бесмодельном режиме**, карточками.
7. **Модель как маршрутизатор** поверх готового.
8. `storage_cleanup`, `explain_delivery`.

Пункт 6 строго до пункта 7: если сначала подключить модель, плейбуки
незаметно начнут от неё зависеть.
