# R+M Envelope v0 — спецификация пакета

**Статус:** черновик для обсуждения
**Дата:** 24 июля 2026
**Основано на:** RM Master Context v3.0 + результаты бенчмарков Bonsai (24.07.2026)

---

## 1. Зачем это нужно

LoRa — очень узкий канал. Полезная нагрузка одного пакета Meshtastic — около
**200 байт** (точное число уточняется на живом железе, см. §9). Обычное сообщение
на русском в UTF-8 тратит 2 байта на букву, то есть в пакет влезает примерно
100 символов текста. Этого мало.

Envelope — это правила, по которым приложение упаковывает смысл в байты так,
чтобы:

- критичное сообщение всегда влезало в **один** пакет;
- одинаковые данные всегда давали **один и тот же** набор байт (иначе не работает
  подпись и проверка целостности);
- потеря части сообщения не уничтожала его смысл;
- получатель мог развернуть пакет на **своём** языке, не полагаясь на перевод.

---

## 2. Принципы

**П1. Структура вместо слов.**
Всё, что можно выбрать из заранее согласованного списка, передаётся кодом, а не
текстом. «Нужна лодка» — это не строка, а один бит.

**П2. Код решает, модель предлагает.**
LLM никогда не определяет приоритет, длину или маршрут пакета. Она только
извлекает структуру, и только через жёсткую схему с ограниченным набором значений.
Обоснование — бенчмарки 24.07: в свободном режиме модели выдумывали значения
(«binaries» вместо бинтов), со схемой — 5/5 корректных извлечений.

**П3. У каждого поля есть потолок.**
Любой список имеет максимальную длину, любое число — диапазон. Без этого маленькие
модели зацикливаются (проверено на 1.7B: список needs повторялся сотни раз).

**П4. Первый фрагмент самодостаточен.**
Если сообщение режется на части, первая часть должна нести законченный смысл.
Остальные — уточнения.

**П5. Критичное не фрагментируется.**
SOS всегда влезает в один пакет. Если не влезает — отрезается хвост, а не режется
на куски.

**П6. Канонический вид.**
Одни и те же данные всегда сериализуются в одинаковые байты: фиксированный порядок
полей, фиксированная разрядность, никаких пробелов и вариативности.
Подпись считается по этим байтам.

## 3. Классы сообщений

Класс определяется **каналом**, а не содержимым (решение от 24.07).

| Класс | Код | Адресация | Шифрование | Фрагментация |
|---|---|---|---|---|
| `SOS` | 0x1 | широковещательный | **нет (решено 24.07)** | запрещена |
| `BEACON` | 0x2 | широковещательный | нет | запрещена |
| `TEXT` | 0x3 | личный, конкретному узлу | сквозное | разрешена |
| `ACK` | 0x4 | личный | сквозное | запрещена |
| `LOCATION` | 0x5 | личный | сквозное | запрещена |
| `REACTION` | 0x6 | личный | сквозное | запрещена |
| `GROUP_TEXT` | 0x7 | групповой (ключ рассылки) | сквозное + подпись | разрешена |
| `GROUP_ROSTER` | 0x8 | групповой | сквозное + подпись создателя | запрещена |
| `GROUP_ACK` | 0x9 | личный (только отправителю) | сквозное | запрещена |

**Классы 0x7–0x9 ЗАРЕЗЕРВИРОВАНЫ 31.07.2026** под групповые чаты
(реализация v2, спека — `docs/group_chats.md`). Резерв сделан сейчас,
потому что незарезервированное место потом не появляется (урок
Крафта v1.0). Поля адресации группы (для будущих тел 0x7–0x9,
зафиксированы заранее):

- `group_id` — 4 байта LE, отпечаток ключа группы (усечённый);
- признак «групповое / один на один» отдельным битом НЕ вводится:
  признаком является сам класс пакета (0x7–0x9 — групповые);
- `roster_version` — 2 байта LE, версия состава группы, монотонная;
  идёт в каждом GROUP_TEXT: получатель с другой версией видит
  расхождение явно (см. group_chats.md), пакет не «проглатывается».

Текущие реализации при получении классов 0x7–0x9 обязаны их молча
игнорировать (версия конверта не меняется, провод старых классов
не затронут).

**`REACTION` (зарезервирован v1.1, 29.07.2026):** реакция-эмодзи на
сообщение. Тело: `[msg_id реагируемого: 2 байта LE][индекс эмодзи:
1 байт]` — индекс в замороженной таблице top-255
(`tools/semdict/emoji_v11.json`). Итого 3 байта тела + общий заголовок
(4 байта) = **7 байт пакет**; в sealed-обёртке личного чата — плюс
стандартный оверхед шифрования. Эмодзи вне таблицы реакцией не
отправляется (полноценным TEXT). Реализация UI — после v1.1.

### Модель прогрессивного раскрытия (решено 24.07)

SOS читается всеми — иначе он бессмыслен. Поэтому в эфир уходит минимум,
а подробности открываются адресно и только с согласия пострадавшего.

| | В широковещательном SOS | В личном чате со спасателем |
|---|---|---|
| Факт беды, срочность, травма | да | да |
| Количество людей | да | да |
| Координаты | **грубые** (~300×600 м) | точные (1–2 м), по подтверждению |
| Имя / профиль | нет | по подтверждению |
| Фото, контакты, детали | нет | по решению пользователя |

Раскрытие точных координат и личности — **явное действие пользователя**
в интерфейсе личного чата, не автоматическое.

**Ограничение MVP, которое надо понимать.** Меш-транспорт (Meshtastic) сам по себе
передаёт идентификатор узла на своём уровне — наш формат этого не скрывает.
То есть на MVP анонимность неполная: приложение не прикладывает имя и профиль,
но радиоуровень виден. Полная псевдонимность — задача перехода на Reticulum
(Phase 1.5+).

## 4. Общий заголовок (4 байта)

Присутствует в каждом пакете любого класса.

```
байт 0:  [ версия : 4 бита ][ класс : 4 бита ]
байт 1:  [ флаги : 8 бит ]
байт 2:  [ msg_id : младшие 8 бит ]
байт 3:  [ msg_id : старшие 8 бит ]
```

**версия** — сейчас `0`. Позволяет менять формат, не ломая старые устройства.

**класс** — из таблицы §3.

**флаги** (бит 0 — младший):

| бит | смысл |
|---|---|
| 0 | пакет фрагментирован (за заголовком идёт блок фрагментации, §7) |
| 1 | требуется подтверждение доставки |
| 2 | есть текстовый хвост (§6) |
| 3 | координаты присутствуют |
| 4–7 | зарезервированы, должны быть 0 |

**msg_id** — 16 бит, случайное число, генерируется отправителем.
Нужно для: подтверждений, отбрасывания дубликатов при ретрансляции, сборки
фрагментов. Хранится в порядке от младшего байта к старшему (little-endian)
для всех многобайтовых полей в этой спеке.

## 5. Тело SOS (8 байт)

```
байт 4:  [ severity : 2 бита ][ people_count : 6 бит ]
байт 5:  [ injury : 4 бита ][ hops_left : 4 бита ]
байт 6-7:  широта  грубая (2 байта)
байт 8-9:  долгота грубая (2 байта)
```

Координаты в широковещательном SOS — **намеренно грубые** (см. §3).
Точные передаются позже, в личном чате, классом `LOCATION`.

### severity (2 бита)

| код | значение |
|---|---|
| 0 | low |
| 1 | medium |
| 2 | high |
| 3 | critical |

### people_count (6 бит)

0–62 человека. Значение 63 = «больше 62 / неизвестно».

### injury (4 бита)

| код | значение | код | значение |
|---|---|---|---|
| 0 | нет травмы | 5 | травма головы |
| 1 | кровотечение | 6 | без сознания |
| 2 | перелом | 7 | утопление |
| 3 | ожог | 8 | отравление |
| 4 | укус животного/змеи | 9–14 | резерв |
| | | 15 | другое |

### hops_left (4 бита)

Сколько раз пакет ещё можно ретранслировать. Отправитель ставит 3.
Каждый пересылающий узел уменьшает на 1. При 0 — не пересылать.
Защита от бесконечного хождения сигнала по сети.

### Координаты — два уровня точности

**Грубые (2+2 байта) — для широковещательного SOS:**

```
широта_код  = round((широта  + 90)  / 180 * 65535)
долгота_код = round((долгота + 180) / 360 * 65535)
```

Разрешение (проверено расчётом): **306 м** по широте, **612 м** по долготе на
экваторе. Ячейка примерно 300×600 метров — понятно, куда идти, но нельзя
указать на конкретный дом или палатку.

**Точные (3+3 байта) — только в личном чате, класс `LOCATION`:**

```
широта_код  = round((широта  + 90)  / 180 * 16777215)
долгота_код = round((долгота + 180) / 360 * 16777215)
```

Разрешение: **1.2 м** по широте, **2.4 м** по долготе. Отправляется только
после явного подтверждения пользователем в интерфейсе.

### Правило округления (обязательное, зафиксировано 24.07)

`round` во всех формулах выше — это всегда **floor(x + 0.5)**: прибавить 0.5
и отбросить дробную часть. Ровно половина округляется вверх.

Зачем фиксировать: встроенное округление в разных языках разное. Python
`round()` тянет 0.5 к чётному числу, Swift `rounded()` округляет от нуля.
Если каждая реализация возьмёт «своё» округление, кодеки разойдутся
побайтово — а тогда не совпадут подписи и тест-векторы. Обе реализации
(Python и Swift) обязаны считать floor(x + 0.5).

Если координат нет (нет фикса GPS) — поля заполняются единицами
(`0xFFFF` / `0xFFFFFF`), флаг 3 сбрасывается.

## 5а. Тело ACK (2 байта)

```
байт 4-5: msg_id подтверждаемого сообщения (LE)
```

Узел, получивший пакет с флагом 1 («требуется подтверждение»), отвечает
пакетом класса `ACK`. Эти два байта — msg_id того сообщения, которое
подтверждается. msg_id в общем заголовке самого ACK — свой, новый.

---

## 5б. Тело BEACON (3 байта, опционально +4)

BEACON — маячок статуса после SOS. Его шлёт **сам пострадавший**, чтобы
на карте у спасателей была свежая картина.

```
байт 4-5:  msg_id исходного SOS (LE)
байт 6:    [ статус : 2 бита ][ число откликнувшихся : 6 бит ]
байт 7-10: грубые координаты (опционально, если установлен флаг 3)
```

### статус (2 бита)

| код | значение |
|---|---|
| 0 | всё ещё нужна помощь |
| 1 | помощь идёт |
| 2 | ситуация решена |
| 3 | резерв |

### число откликнувшихся (6 бит)

0–62. Значение 63 = «много».

**Важное правило.** Статус выставляет только сам пострадавший. Число
откликнувшихся — это не статус: пока человек сам не переключил на
«помощь идёт», по умолчанию остаётся «нужна помощь», сколько бы
откликов ни пришло.

Координаты добавляются, если человек переместился: флаг 3 и те же
грубые 2+2 байта, что в SOS.

## 6. Потребности и текстовый хвост

### needs — битовая маска (2 байта, только для SOS)

Идёт сразу после тела SOS. 16 позиций, можно выбрать любое сочетание.

| бит | потребность | бит | потребность |
|---|---|---|---|
| 0 | бинты / перевязка | 8 | связь |
| 1 | вода | 9 | тепло / одежда |
| 2 | еда | 10 | инструмент |
| 3 | лодка | 11 | помощь в переноске |
| 4 | транспорт (наземный) | 12 | топливо *(добавлено 25.07.2026)* |
| 5 | врач / медик | 13 | укрытие *(добавлено 25.07.2026)* |
| 6 | лекарства | 14 | резерв |
| 7 | эвакуация | 15 | другое (см. хвост) |

Справочник требует проверки на реальных сценариях Вьетнама и Бали — см. §9.

**Соответствие enum-строкам модели.** Схема SOS-извлечения выдаёт значения
`bandages, water, food, boat, vehicle, doctor, medicine, evacuation, fuel,
shelter` — каждое обязано иметь бит. Машиночитаемая таблица соответствия —
`tests/needs_mapping.json` (единственный источник; Python и Swift сверяются
с ним тестами). Биты 12 (топливо) и 13 (укрытие) заняты 25.07.2026 из
резерва, чтобы справочники модели и envelope совпадали 1-в-1.

### Текстовый хвост (переменной длины)

Присутствует, если установлен флаг 2. Формат:

```
[ кодек : 1 байт ][ длина : 1 байт ][ байты текста ]
```

**кодек** — каким способом сжат текст. Решение 24.07: кодек сменный,
его номер передаётся прямо в пакете, чтобы стороны не должны были
договариваться заранее:

| код | способ |
|---|---|
| 0 | без сжатия, UTF-8 как есть (по умолчанию) |
| 1 | zlib / deflate (есть в стандартных библиотеках всех платформ) |
| 2 | коды протокола Smysl (словарь rm_dict v0) — байты RMCodec; получатель разворачивает словарём на своём языке *(занят 27.07.2026; Python-симулятор пока не разворачивает)* |
| 3–255 | резерв. Кандидат — zstd с предобученным словарём, см. §9 |

**длина** — число байтов текста после сжатия. Длину считает код,
не модель (принцип из §7).

Для SOS хвост допустим только если весь пакет остаётся в пределах одного
LoRa-пакета. Иначе хвост отбрасывается целиком (принцип П5).

## 7. Фрагментация (только TEXT)

Если флаг 0 установлен, сразу за общим заголовком идут 2 байта:

```
байт 4: номер фрагмента (от 0)
байт 5: всего фрагментов
```

Правила:

- максимум 16 фрагментов на сообщение;
- сборка по `msg_id`;
- неполное сообщение хранится 10 минут, потом отбрасывается;
- фрагменты могут прийти в любом порядке;
- дубликаты отбрасываются;
- **длину считает код, а не модель** (бенчмарки 24.07: модели ошибались
  в подсчёте символов втрое и не могли уложиться в заданный лимит).

## 8. Тест-векторы

Обязательны для проверки совместимости двух реализаций.

### ТВ-1. Минимальный SOS без координат и хвоста

Вход:
```
класс = SOS, severity = critical, people = 3, injury = кровотечение,
needs = {бинты, лодка}, координат нет, hops_left = 3
```

Ожидаемые байты (**12 всего**):
```
01 00 A7 3B C3 13 FF FF FF FF 09 00
```

Разбор:
```
01     версия 0, класс 1 (SOS)
00     флаги: без фрагментации, без хвоста, без координат
A7 3B  msg_id = 0x3BA7 (пример)
C3     severity=3 (critical), people_count=3
13     injury=1 (кровотечение), hops_left=3
FF FF  широта отсутствует
FF FF  долгота отсутствует
09 00  needs: биты 0 и 3 = бинты + лодка
```

### ТВ-2. Тот же SOS с грубыми координатами

Координаты: широта 8.7100, долгота 115.1700 (Бали, для примера).

```
широта_код  = round((8.71 + 90) / 180 * 65535)  = 35939 -> 63 8C (LE)
долгота_код = round((115.17 + 180) / 360 * 65535) = 53733 -> E5 D1 (LE)
```

Обратное преобразование: 8.7109 / 115.1687 — смещение около **100 и 145 метров**.
Это ожидаемо и является целью: точка «где-то здесь», а не «вот тут».

Флаг 3 установлен → байт флагов = `08`. Полный пакет (12 байт):
```
01 08 A7 3B C3 13 63 8C E5 D1 09 00
```

### ТВ-2б. Точные координаты в личном чате (класс LOCATION)

```
широта_код  = round((8.71 + 90) / 180 * 16777215)  = 9200438  -> 36 63 8C (LE)
долгота_код = round((115.17 + 180) / 360 * 16777215) = 13755918 -> 0E E6 D1 (LE)
```

Обратное преобразование даёт ровно 8.71000 / 115.17000 — потерь нет.

### ТВ-3. Проверка канонической сериализации

Одна и та же структура, собранная дважды (в разном порядке заполнения полей),
обязана дать **байт в байт** одинаковый результат. Проверяется автотестом.

### ТВ-4. Фрагментация

Текст длиной 500 байт после сжатия → разбить, перемешать порядок,
потерять один фрагмент, убедиться что:
- сообщение не собирается (правильно);
- после повторной отправки потерянного — собирается;
- дубликат не ломает сборку.

## 9. Открытые вопросы

**Закрыто 24.07:** шифрование SOS (не шифруем), раскрытие личности и точных
координат (только в личном чате, по подтверждению пользователя).
Дополнено 24.07: правило округления координат (§5), тела ACK и BEACON
(§5а, §5б), сменный кодек сжатия текста (§6).

1. **Точный лимит полезной нагрузки** Meshtastic на ThinkNode M1 — измерить на
   железе, когда приедет. От этого зависит потолок хвоста.

2. **Грубость координат.** 300×600 м — правильный баланс? На плотном пляже это
   может быть сотня людей, в джунглях — приемлемо. Возможно, стоит дать
   пользователю выбор точности в момент отправки.

3. **Утечка идентификатора на уровне транспорта.** Meshtastic передаёт ID узла
   сам по себе. Насколько это обесценивает нашу модель раскрытия и можно ли
   что-то сделать в рамках MVP — проверить на живом железе.

4. **Справочник потребностей.** 16 позиций — достаточно ли и те ли?
   Нужен сбор реальных сценариев (Вьетнам, Бали).

5. **Словарь сжатия.** Решение 24.07: в v0 кодек сменный (без сжатия / zlib,
   см. §6). zstd с предобученным словарём — вопрос на будущее: на каких
   текстах обучать словарь и как обновлять его без потери совместимости
   со старыми версиями приложения.

6. **Частота маячка статуса** после SOS: часто (свежая картина, расход батареи)
   или редко (экономно, карта устаревает).

7. **Порядок байтов** зафиксирован как little-endian — проверить, что это
   не конфликтует с внутренними соглашениями Meshtastic.
