# Архитектура LLM-слоя: сменная модель, сменный движок

Дата решения: 25.07.2026. Код: `ios/RM/RM/LLM/`.

## Зачем

Модели появляются и устаревают быстро (за один вечер 24.07 проект сменил
Bonsai 8B на Qwen3-4B). Привязываться к одной модели или одному движку —
ошибка. Поэтому:

- **модель — заменяемая деталь**: файл + конфиг, не код;
- **движок — заменяемая деталь**: за протоколом `LLMProvider`;
- приложение работает с **любой GGUF-моделью подходящей архитектуры**,
  не только с одной конкретной.

Спор «какая модель лучше» перестаёт быть окончательным: новая модель —
это смена файла в конфиге, новый движок — новый провайдер, без ломки
остального.

## Устройство слоя (4 файла)

```
ios/RM/RM/LLM/
├── LLMProvider.swift            протокол + типы запросов/ответов/ошибок
├── LLMModelConfig.swift         конфиг модели + фабрика провайдеров
├── StructuredLLM.swift          служебные вызовы: схема ИЛИ валидация+repair
└── Providers/
    └── LlamaCppProvider.swift   реализация №1 (каркас, точки интеграции)
```

### Протокол `LLMProvider`

Actor-протокол, скрывающий конкретный движок и формат модели:

| Метод | Что делает |
|---|---|
| `load(_ config:)` | загрузка модели по пути из конфига (повторный вызов перезагружает) |
| `unload()` | выгрузка и освобождение памяти (jetsam на iOS) |
| `generate(_:)` | свободная генерация (чат, переводы) |
| `generateStructured(_:spec:)` | генерация под жёсткой схемой (грамматика на сэмплере) |
| `cancelActiveGeneration()` | прервать текущую генерацию (nonisolated, можно из UI) |

Плюс два **объявляемых свойства**: `kind` (какой движок) и `capabilities`
(что умеет). Отмена работает и кооперативно (отмена Task), и явно (кнопка «Стоп»).

### Ключевое решение: structured output — опциональная возможность

Протокол **не предполагает, что грамматика есть всегда**. Провайдер объявляет
её через `capabilities.contains(.structuredOutput)`:

- **llama.cpp** — объявляет: GBNF-грамматика работает на устройстве на уровне
  сэмплера (зануляет недопустимые токены — жёсткая гарантия формата);
- **MLX** — вопрос открыт (guided generation там молодой), поэтому
  MLXProvider сможет честно НЕ объявить schemу — и всё продолжит работать
  через запасной путь.

### Запасной путь: `StructuredLLM.call(...)`

Все служебные вызовы (SOS→JSON, сжатие, перевод) идут через одну точку —
`StructuredLLM.call`. Она закрепляет принципы проекта на уровне абстракции:

1. если провайдер умеет схему → `generateStructured` (грамматика);
2. если НЕ умеет → свободная генерация, из текста вырезается JSON;
3. **в обоих случаях** результат парсится в Swift-тип (`Decodable` —
   Swift-enum сам отсекает значения вне набора) и проходит семантическую
   валидацию кодом (потолки, диапазоны — правила №3, №4 CLAUDE.md);
4. не прошло → **repair-попытка**: модели показывают её ответ, причину
   отказа и схему текстом, просят исправить (по умолчанию 1 попытка);
5. не помогло → `LLMError.invalidStructuredResult` — вызывающий код
   обрабатывает отказ явно, никакой тихой деградации.

Валидация выполняется даже когда грамматика есть: грамматика гарантирует
формат, но не смысл (правило №8 — случай «head» вместо «bleeding»).

### Спецификация схемы: `StructuredSpec`

- `jsonSchema` — канонический источник (JSON Schema с enum и maxItems);
- `gbnf` — предкомпилированная грамматика для llama.cpp. Для статических
  схем (SOS) она генерируется **офлайн** скриптом
  `examples/json_schema_to_grammar.py` из llama.cpp и зашивается в
  приложение строкой. Конвертер json_schema→GBNF на устройстве не нужен.

## Выбор модели: конфиг, не хардкод

`LLMModelConfig` (Codable) хранится в
`Application Support/Models/llm_config.json`:

```json
{
  "providerKind": "llamaCpp",
  "modelFile": "Qwen_Qwen3-4B-Instruct-2507-Q4_K_M.gguf",
  "displayName": "Qwen3-4B-Instruct-2507 (Q4_K_M)",
  "contextLength": 4096,
  "sampling": { "temperature": 0.5, "topP": 0.85, "topK": 20, "minP": 0 },
  "expectsStructuredOutput": true
}
```

- `LLMModelConfig.loadActive()` читает конфиг; нет файла — дефолт
  (текущее решение проекта: Qwen3-4B Q4_K_M через llama.cpp).
- `modelFile` — относительный путь в каталоге моделей приложения:
  подложил другой GGUF + поправил конфиг — работает другая модель.
- `expectsStructuredOutput` — подсказка для UI (предупредить о движке без
  схемы до загрузки); истина в рантайме — всегда `provider.capabilities`.
- Сэмплинг по умолчанию — тот же, что в `tools/bench_http.py`:
  результаты на телефоне сравнимы с бенчмарками на Маке.

`LLMProviderFactory.make(kind)` — единственное место, где тип движка
превращается в класс.

## Реализация №1: LlamaCppProvider (основной путь)

Статус: **каркас собран и компилируется**, пакет llama.swift ещё не
подключён. До подключения `load()` честно кидает
`LLMError.providerUnavailable` — UI показывает состояние, а не падает.

Что уже есть: проверка файла модели, объявленные возможности
(`structuredOutput` + `cancellation`), приоритет предкомпилированной GBNF,
атомарный флаг отмены, целевой скелет цикла генерации в комментариях
«ИНТЕГРАЦИЯ:» (какие C-вызовы куда встают).

Шаги полной интеграции (когда дойдём):
1. SPM: `https://github.com/mattt/llama.swift`, `from: "2.10107.0"` (iOS 16+).
2. Заполнить точки «ИНТЕГРАЦИЯ:» в `load/unload/run`.
3. Сгенерировать GBNF из SOS-схемы офлайн, зашить в `StructuredSpec`.
4. Entitlement Increased Memory Limit (модель 2.4 ГБ + KV-кэш).
5. Прогнать 7 тестов методики на iPhone (сравнить с `bench_results_qwen3_4b.json`).

## Реализация №2: MLXProvider (задел, не пишем)

Место оставлено: case `.mlx` в `LLMProviderKind` и ветка в фабрике,
которая пока кидает `providerUnavailable`. Когда решим пробовать
(MLX быстрее llama.cpp на ~40–60% на Apple Silicon — см.
`qwen_ios_path.md`):

1. Новый файл `Providers/MLXProvider.swift`: `actor MLXProvider: LLMProvider`.
2. Зависимость `ml-explore/mlx-swift-lm`; модель — папка MLX-формата
   (`mlx-community/Qwen3-4B-Instruct-2507-4bit`, 2.26 ГБ) — `modelFile`
   это уже умеет (путь, не «файл GGUF»).
3. Главный вопрос — схема: если `MLXGuidedGeneration` подтвердится —
   объявить `.structuredOutput`; если нет — НЕ объявлять, и служебные
   вызовы автоматически поедут через валидацию+repair в `StructuredLLM`.
   Ничего в остальном коде менять не придётся — в этом весь смысл.
4. Ветка в фабрике: `return MLXProvider()`.

Тот же рецепт — для любого третьего движка (и для возвращения Bonsai,
если у её iOS-пути соберётся рантайм: это будет просто ещё один провайдер).

## Границы SOS-извлечения (правило №9)

SOS инициируется **только явным действием пользователя** (кнопка SOS).
`SOSExtraction` — помощник заполнения формы, не классификатор:

- модель получает текст ТОЛЬКО после того, как человек сам открыл SOS-поток;
- результат извлечения — черновик, который человек видит и подтверждает
  перед отправкой; автоотправка запрещена;
- прогонять входящие/произвольные тексты через SOS-извлечение, чтобы
  «понять, не бедствие ли это», — запрещено. Схема принуждает заполнить
  все поля (needs: minItems=1), поэтому даже мирный рассказ про поход
  даёт «needs: [bandages]» — выход модели в принципе не годится как триггер.

Защита от регресса при смене модели/движка/промпта — общие тест-векторы
`tests/sos_extraction_vectors.json`: позитивный контроль (настоящий SOS)
и негативный (рассказ про поход с «тревожными» словами). Гоняются тестом
6б в `tools/bench_http.py`; Swift-реализация обязана использовать тот же файл.

## Правила проекта, закреплённые в этом слое

- №2 (только структурированный вывод в служебных функциях) → `StructuredLLM.call`
  — единственная дверь для SOS/сжатия/переводов.
- №3 (потолки повторяемых полей) → в JSON Schema + семантическая валидация кодом.
- №4 (длину считает код) → валидатор вызывающего кода, не модель.
- №8 (enum-значения в промпте) → зона ответственности вызывающего кода;
  напоминание зашито в док-комментарий `generateStructured`.
- LLM вне доверенного пути (№1) — слой не имеет доступа к ключам и
  транспорту; он только генерирует текст/JSON по запросу.
