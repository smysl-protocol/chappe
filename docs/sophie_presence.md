# R+M — Кая: сквозное присутствие LLM

**Статус:** проектное решение
**Дата:** 26 июля 2026
**Связано:** docs/llm_architecture.md (модель), docs/semantic_compression.md (конвейер), docs/RM_Envelope_v0.md (транспорт)

---

## 0. Идея в одном абзаце

Кая — один локальный ассистент в двух формах присутствия: **(а) свои чаты** — папка «Кая», чатов сколько угодно, структурно как у Claude/GPT; **(б) шёпот @Кая** — вызов внутри любой переписки с человеком, где вопрос и ответ видит только вызвавший. Одна модель (Qwen3-4B на устройстве), ноль байт в эфир от любой активности Каи.

---

## 1. Два разных понятия: история и рабочее окно

Модель stateless — у неё нет «памяти между чатами», промпт собирается заново на каждый вызов. Отсюда:

- **Историй чатов — неограниченно.** Это записи в локальной БД; модель к их количеству равнодушна. Чаты физически не протекают друг в друга, потому что в промпт попадает только выбранный чат.
- **Рабочее окно — узкое.** Qwen3-4B Q4 ≈ 2.5 ГБ; на iPhone после загрузки модели реалистичный бюджет контекста **4–8k токенов** (≈15–30 последних сообщений). Числа проверить на устройстве.
- **Память чата (суммарий) — реализовано 27.07.2026.** Всё, что старше окна, фоново сворачивается в абзац фактов («о чём чат, что решили, ключевые имена/числа»). Промпт = системный + суммарий + скользящее окно. Суммарий обновляется инкрементально и хранится локально рядом с чатом. Код: `SophieSummarizer.swift` — триггер >1500 токенов за окном, чанки ~1200, курсор в состоянии суммария, вытеснение P0–P2 с продолжением с курсора, политика «на зарядке или батарея >30%», лимит 120 слов держит код; промпт свёртки — `prompts/sophie_summary_ru.txt`.
- **KV-кэш** держим только для активной сессии (llama.cpp session save/load) — убирает прогрев на каждый ответ. Кэши неактивных чатов не храним в RAM, при переключении пересобираем из истории.

Честные ожидания: 4B в длинном многотемном разговоре плывёт раньше фронтир-моделей. Окно+суммарий это сдерживает, но Кая — бытовой ассистент, не Клод; вчерашние прогоны (SOS-извлечение, пивот) показывают, что для этой роли её хватает.

- Внутри чата доступна диктовка как обычно (триггер @ не нужен — весь чат и так с Каей).
- Ответы Каи в её чатах могут использовать инструменты (§4).

### 2.1. Предустановленные чаты (реализовано 26.07.2026)

Четыре закреплённых чата по дизайну (design/sophie, блок «всегда под
рукой»): **О приложении / Связь / Первая помощь / SOS**. Отвечают из
курированных локальных баз (`Resources/sophie_kb/*.md`), а не из весов
модели: детерминированный ретривер выбирает секции под запрос, модель
пересказывает только выдержки, чего нет в базе — честное «не знаю»
и темы из оглавления. Формат баз, алгоритм выборки и промпт — в
**docs/kb_spec.md** (источник истины). Чаты не удаляются, историю
можно очистить; у каждого своя история и привязка к паку. Паки
«О приложении» и «Связь» правятся под реальность каждым релизом
(правило спеки «никаких выдуманных возможностей»).

## 3. Шёпот @Кая в переписке с человеком

> **Фаза 2б реализована (27.07.2026), в демо-чате:** настоящих личных
> чатов ещё нет — шёпот живёт во вкладке «Чат» (демо-собеседник;
> исходящие честно кодируются в envelope и ждут узлов в персистентной
> очереди). Реализовано по §3: чип только ручным вводом «@» (программные
> вставки не создают токен — проверено тестом), синий композер с момента
> чипа, искра вместо стрелки, «видно только вам», карточки радиуса 12,
> ветка шёпота в отдельном файле (лог чата не может её захватить —
> свойство хранилища), «В черновик» — единственный путь в сообщение,
> инструменты §4 доступны, ответ через P2. Диктовки в приложении пока
> нет — правило «голосом шёпот не включить» выполняется тривиально.
> Код: `ios/RM/RM/Chat/`.

Смертельный риск здесь не модельный, а интерфейсный: запрос набирается в том же поле, что и сообщения живому собеседнику. Один сбой — и «@Кая что думаешь про его предложение» улетает ему. Поэтому три железных правила:

1. **Видимый режим.** С момента создания токена `@Кая` поле ввода переключается в режим шёпота: **синяя** тонировка всего композера, чип-токен, подпись «видно только вам». Вопрос и ответ рендерятся синими карточками в ленте, помеченными как приватные.
2. **Ноль эфира на уровне архитектуры.** Ветка шёпота не проходит через очередь envelope вообще — это гарантия кода (другой путь данных), а не интерфейса. Шёпоты и ответы не кодируются словарём, не фрагментируются, не ретранслируются.
3. **В сообщение — только явно.** Ответ Каи можно одним действием («В черновик») превратить в текст исходящего сообщения; автоматически — никогда.

Гейт приватности: обещание «ноль байт с устройства» действует только
при локальном провайдере. При provider.kind == .remote (dev-профиль
через Мак) шёпот помечается dev-only и недоступен в пользовательской
сборке. **Гейт открыт 26.07.2026**: defaultConfig = localQwen (модель
на устройстве, фаза 2 подтверждена — docs/reports/ondevice_phase2.md),
условие в коде — `LLMModelConfig.allowsPrivateWhisper`. Dev-профиль
remote переключается только вручную в dev-меню и гейт закрывает.

### 3.1. Правила триггера (критично)

- Токен создаётся **только ручным вводом с клавиатуры**: символ `@` + `K`/`К` → автоподхват `@Кая`/`@Kaya` (чип). Цвет меняется **в момент создания чипа**, до отправки.
- **Программные вставки текста не могут создать токен.** Диктовка (STT) вставляет текст программно — значит, голосом режим шёпота включить нельзя в принципе (заодно решается «@ = "собака"» в транскрипции). Реализация: различать keystroke-события и setText.
- Диктовка **разрешена после** ручного создания токена — надиктовать сам вопрос можно.
- Удаление чипа мгновенно возвращает обычный режим и цвет.
- `@` в середине набранного сообщения без чипа — просто символ, ничего не подсвечиваем.

### 3.2. Контекст шёпота

Окно текущей переписки + её суммарий + инструменты (§4) + сам вопрос. Кая видит разговор, но её ответ живёт в приватной локальной ветке (шифрованное хранилище приложения), в общий лог чата не пишется, при экспорте/пересылке чата не участвует.

## 4. Инструменты (детерминированные, без эфира)

Ящик маленький и весь read-only к уже имеющимся данным:

| Инструмент | Источник | Примечание |
|---|---|---|
| Моя позиция | GPS устройства | |
| Последняя позиция собеседника | защищённый слой из уже принятых пакетов | Кая обязана называть возраст данных («по данным 40 минут назад») |
| Расстояние/время пешком | формула (гаверсинус ÷ 4.5 км/ч) | считает код, модель только формулирует; маршрутизацию по дорогам не обещаем |
| Батарея, качество канала, время | системные API | |

**Правило радио-тишины:** инструменты не создают эфир. Если позиции собеседника нет или она устарела, Кая говорит об этом и может *предложить* отправить запрос позиции — отправка только явным действием человека, обычным путём через envelope.

Вызов инструментов — строгой JSON-схемой (тот же приём, что в SOS-извлечении).

Требования к вызову: StructuredLLM.call; enum-значения всех полей
перечисляются в промпте (правило №8 CLAUDE.md); при отсутствии
capability structuredOutput — валидация кодом + repair.

## 5. Планировщик модели (единственный новый компонент)

> **Фаза 1 реализована (26.07.2026):** `ModelScheduler` — один слот,
> очередь приоритет+FIFO, P0–P2 мгновенно вытесняет P3
> (cancelActiveGeneration). Существующие вызовы переведены: SOS → P0,
> дев-запуски → P1, чат Каи → P2; P3-задач пока нет. Покрыто тестами
> (ModelSchedulerTests). Окно истории Каи (§1) — базовая версия
> с бюджетом ~3000 токенов, суммарий не реализован.

Модель одна, желающих много. Очередь с приоритетами и вытеснением:

```
P0  SOS-конвейер (извлечение/подтверждение)
P1  Исходящее сообщение (пивот+коды: человек ждёт отправки)
P2  Интерактив Каи (шёпот, её чаты) — FIFO
P3  Фоновые суммаризации — прерываемые, чанками
```

P3 всегда уступает мгновенно (суммаризация идёт кусками с сохранением позиции). Опционально: P3 только на зарядке / при батарее >30%.

Фазность: планировщик работает на текущем LLMProvider — вытеснение
P3 через cancelActiveGeneration(). Чанк-суммаризация — уровень
приложения: каждый чанк отдельный вызов, курсор хранит приложение
(БД), расширения протокола не требует. Session save/load (KV-кэш) —
оптимизация прогрева, опциональная capability фазы 2, не пререквизит.

## 6. Проверка: не ломает ли это прежнюю архитектуру

| Компонент | Влияние |
|---|---|
| Envelope / транспорт | **Не меняется.** Шёпот и чаты Каи не создают пакетов (0 байт). Формат нетронут. |
| Словарь / кодек | **Не участвует.** Шёпот не кодируется. (Позже суммаризация может переиспользовать пивот-приём — опция, не зависимость.) |
| SOS-конвейер | **Не задет.** P0 в планировщике; фоновые задачи вытесняются. Ложные SOS-триггеры Каи невозможны — шёпот не имеет пути в эфир. |
| Модель | Та же Qwen3-4B, тот же инстанс. Новое — планировщик поверх + опциональная capability KV-сессий (фаза 2). Дистрибуция шёпота гейтится локальным провайдером. |
| Память устройства | 2.5 ГБ модель + один KV-кэш активной сессии; кэши остальных чатов не держим. Проверить на реальном iPhone. |
| Приватность | Шёпоты и суммарии — локальное шифрованное хранилище, не синхронизируются, не экспортируются с чатом. |

**Вердикт: ничего не ломает.** Добавляются два элемента: планировщик задач модели и приватное хранилище веток Каи. Оба — новые модули поверх, не правки существующих.

## 7. Открытые вопросы

1. Групповые чаты: шёпот работает так же (видит только вызвавший) — подтвердить UX.
2. Резерв `@` под упоминания людей в будущем: чип Каи должен жить в одном пространстве с ними без конфликтов.
3. Бюджет P3 (батарея/тепло): политика по умолчанию.
4. Голосовой вызов Каи *вне* поля ввода (кнопка-микрофон в её чатах) — отдельный UX, триггер-правило там не нужно.
