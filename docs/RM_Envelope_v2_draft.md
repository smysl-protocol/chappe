# Envelope v2 — черновик ревизии формата (рэтчет Б + адресация релея)

Статус: **черновик к реализации**, 02.08.2026. Основание: ADR 007
(принят вариант Б), решение владельца «конверт проектируем один раз».
Спека v0/v1 (`RM_Envelope_v0.md`) не редактируется — v2 описан здесь,
при реализации вливается в основную спеку отдельной задачей.

## Цели ревизии (обе в одной смене версии, второй не будет)

1. **Рэтчет Б**: сессионные сообщения без эфемерного ключа и nonce —
   обвязка 23 Б вместо 93 Б.
2. **Адресация для релейного транспорта**: по интернету заголовка
   Meshtastic нет — «кому» должен уметь жить в нашем конверте.
   По радио адресация остаётся у Meshtastic — на LoRa ревизия
   не добавляет ни байта.

## Заголовок

Версия = 2. Раскладка байтов 0–3 как в v1: `[ver⁴|class⁴][flags][msgID LE]`.
Приёмник v2 принимает версии 0–2.

Флаги: биты 0–3 как в v1 (frag, ackReq, hasTail, hasCoords).
**Бит 4 = hasAddress** (новый, допустим только при ver=2; для ver≤1
биты 4–7 по-прежнему обязаны быть нулями — правило валидации
становится зависимым от версии). Биты 5–7 зарезервированы, нули.

## Адресный блок (только при hasAddress)

Сразу после заголовка, до блока фрагментации и потока:

| Поле | Б | Содержимое |
|---|---|---|
| dst | 8 | **суточный псевдоним ящика**: `SHA-256(pubkey получателя ‖ unix-день)[0..8]` |

Статический dst сводил бы на нет вращение тега сессии — релей
группировал бы диалог по dst (замечание владельца 02.08). Поэтому dst
**вращается по суткам**: вычислим любым, кто знает pubkey получателя
(отправителю этого достаточно), релею pubkey неизвестен — связать
псевдонимы разных суток он не может. Получатель опрашивает ящики за
сегодня ± 2 суток (перекос часов + 48 ч хранения = 3 запроса).
Внутри одних суток связываемость у релея остаётся — записано в
принятых утечках ниже и в relay_spec. Коллизия 8 Б (2⁻⁶⁴) даёт лишь
лишнюю доставку, которую получатель отбросит по AEAD. Отправителя в
открытом виде нет нигде. По радио hasAddress=0.

## Кодеки payload (первый байт потока после метки времени)

| Код | Название | Состояние |
|---|---|---|
| 0 | store | как было |
| 1 | zlib | как было |
| 2 | semantic | как было |
| 3 | sealed | как было — рукопожатие, незнакомцы, самолечение |
| **4** | **session** | **новый: сообщение эпохи (рэтчет Б)** |

## Кодек 4 — session

```
[4][тег сессии 4][счётчик 2 LE][шифртекст][тег AEAD 16]
```

Решение владельца 02.08 (№5 закрыт): **метка времени — внутри
шифртекста** для кодеков 3 и 4 (4 Б unix-минут первым полем открытого
текста). Плейнтекстовой метки в потоке для этих кодеков нет; кодеки
0–2 сохраняют раскладку v1. Цена 0 Б (байты переезжают, не
добавляются), утечка «когда» перед релеем закрыта.

- **Тег сессии** — вращающийся: `HMAC(chain_key_epoch, счётчик)[0..4]`.
  Наблюдателю выглядит случайным; получатель сопоставляет перебором
  своих сессий × окно счётчиков (контактов единицы — дёшево).
  Связываемости диалога на проводе нет (свойство v0/v1 сохранено).
- **Счётчик** — номер сообщения в эпохе, сбрасывается на ре-ключе.
  До расшифровки служит дедупом ветвления радио+релей: виденный
  (сессия, счётчик) отбрасывается. 2 Б ≫ K=100 — запас на два порядка.
- **Ключ и nonce** сообщения выводятся из цепочки KDF по счётчику —
  на проводе их нет.
- Внутри шифртекста: `[внутренний кодек 1][смысл]` — pubkey
  отправителя НЕ передаётся (следует из сессии; поглощение В, ADR 007).

Рукопожатие/ре-ключ/самолечение — кодек 3 (sealed) как сегодня,
внутри шифртекста добавляется ratchet-init блок (маркер, seed эпохи,
стартовый счётчик) — детали на реализации, провод sealed не меняется.

### Предвычисление вращающегося тега получателем

Получатель держит на каждую сессию таблицу кандидатов
`тег → (сессия, счётчик)` для счётчиков `[n, n + MAX_SKIP)`, где n —
следующий ожидаемый; плюс теги уже пропущенных счётчиков < n живут
вместе с их отложенными ключами до TTL. Объём: 128 тегов × число
сессий (контактов единицы) — сотни записей, пересчёт инкрементальный
(сдвиг окна на приёме).

- **Совпадение тега — только кандидат, не факт.** Истина решается
  расшифровкой: тег AEAD (16 Б) либо сходится, либо нет.
- **Коллизия тегов между диалогами** (4 Б, ~10³ кандидатов против
  2³²: вероятность на входящее ≈ 10⁻⁶): пробуются ВСЕ совпавшие
  кандидаты по очереди — цена лишняя попытка расшифровки, ошибочная
  доставка невозможна по построению.
- **Рассинхронизация** (тег не найден ни в одном окне): пакет не
  для нас, либо дыра глубже MAX_SKIP, либо мёртвая сессия. Порядок
  действий: попытка разобрать как кодек 3 (рукопожатие) → если и это
  не наше, для адресного (relay) сообщения отправляется запрос
  повторного рукопожатия (самолечение), для радио-подслушанного —
  молча отбросить (это чужой трафик, NACK был бы утечкой).

## Размеры (обвязка = всё, кроме смысловых байт)

| Сообщение | v1 сегодня | v2 session (радио) | v2 session (релей, +dst 8) |
|---|---|---|---|
| «ок» (4 Б смысла) | 106 | **36** | 44 |
| Отель (35 Б смысла) | 137 | **67** | 75 |
| Обвязка на сообщение | 102 | 32 | 40 |

Параметры рэтчета (подтверждены рекомендацией ADR 007, финализируются
на реализации): ре-ключ K=100 сообщений, MAX_SKIP=128, TTL пропущенных
ключей 14 дней, самолечение после молчания N=14 дней.

## Принятые утечки (осознанно, не по умолчанию)

1. **Длина сообщения видна радио-наблюдателю (LoRa)** — принято:
   каждый байт эфира дорог, паддинг там не заказан. С 09.08 (ревизия
   B, решение владельца по №7) на БЫСТРЫХ транспортах (релей, BLE,
   Wi-Fi Aware, локальная сеть) длина ЗАКРЫТА: обёртка транспортного
   слоя `[0xAD][длина u16 LE][кадр][случайный хвост]` добивает кадр
   до бакета 256 Б — вне конверта, кодек не задет. ЧЕСТНО: паддинг
   закрывает только длину; тайминги и частоту сообщений — нет (см.
   пункт 3).
2. **Связываемость внутри суток у релея**: все сообщения диалога за
   одни сутки попадают в один ящик-псевдоним. Межсуточная связка
   требует знания pubkey получателя, которого у релея нет; тайминг- и
   размер-корреляции остаются возможными (в relay_spec).
3. **Факт и время выхода в эфир** видны наблюдателю всегда (природа
   радио); метка отправки при этом спрятана в шифртекст (№5 закрыт).
4. **Оффер знакомства — стабильный идентификатор, пока открыт «Мой
   код»** (ревизия B, хвост владельца 09.08): кадр RMINTR1/offer несёт
   имя и ключ открыто и повторяется каждые ~4 с — наблюдатель эфира
   привязывает телефон к личности на всё время открытого экрана.
   Принято: смысл оффера — быть прочитанным незнакомцем; граница —
   объявление идёт ТОЛЬКО при открытом экране знакомства (вне его в
   эфире лишь service UUID). Ответ с 09.08 запечатан (RMINTR2,
   эфемерный ключ на каждый ответ и повтор) — согласившийся в эфире
   не светится.
5. **16-битный тег отправителя в sealed2 (кодек 5)** — принятая,
   обоснованная утечка (ревизия B, подпись владельца 11.08, шов
   `docs/reports/wire_revision_b_location_seam.md`): выигрыш против
   прежнего полного 32-байтного ключа отправителя в каждом
   не-session кадре. Вывод — вариант Т1: тег вращается по эпохам
   пары (`HMAC(pairKey, "sender-tag" ‖ epoch)[0..2]`, машинерия
   MailboxID) — наблюдатель видит 2 байта, несвязываемые между
   сутками и получателями; утечки сверх факта кадра нет. Коллизию
   тега среди известных контактов разруливает AEAD (try-all-keys,
   не тот ключ — не расшифруется); незнакомцу тег не даёт ничего,
   новый контакт из кадра с тегом не рождается (полный ключ — только
   рукопожатие/первый кадр, шов B2).

Открытых вопросов формата не осталось; параметры K/MAX_SKIP/TTL —
константы реализации.

## Совместимость и порядок ввода

- Приёмник v2 читает v0/v1 без изменений; v1-приёмник, получив v2,
  честно падает на «неизвестная версия» — обновление обоих концов
  до начала сессий (пока парк = два наших телефона, это дёшево).
- Заморозка словаря (FREEZE.md) и эта ревизия независимы: хеш таблицы
  0xEE остаётся в смысловых байтах кодека 2 как есть.
- Тест-вектора: `tests/envelope_test_vectors.json` дополняются
  v2-векторами (session-кадр, адресный блок, вращающийся тег) —
  Python↔Swift побайтово, как заведено.
