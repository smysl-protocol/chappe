## 0. Постановка в одном абзаце

Релей — почтовый ящик, получатель сам опрашивает его (3 с активным,
12 с свёрнутым). Спящий iPhone iOS замораживает целиком через
секунды после гашения экрана — опроса нет никакого, это правило Apple
для всех приложений. Легальных способов разбудить спящий телефон у
iOS два: событие Bluetooth (у нас уже включено — LoRa-узел будит
приложение; в интернет-тесте радио было выключено) и **пуш через
серверы Apple (APNs)**. Эта спека вводит второй способ: релей при
укладке кадра в ящик шлёт через APNs пустой сигнал «проснись»,
телефон показывает уведомление и забирает почту.

## 1. Что видит Apple, что видит релей — граница честно

Схема Signal, принятая здесь за образец: **через Apple не проходит
ни байта содержимого**.

| Сторона | Что узнаёт нового | Чего НЕ узнаёт |
|---|---|---|
| **Apple (APNs)** | приложению com.chappe.app на устройстве X пришло «что-то» в момент T; частота таких событий | содержимое, отправителя, ящик, текст уведомления с расшифровкой (текст — локализованная константа из бандла, см. §3) |
| **Релей** | связку «пуш-токен устройства ↔ ящики, на которые он подписан» — то есть **явную склейку всех пар и всех эпох одного получателя** | по-прежнему ничего внутри AEAD: ни текста, ни отправителя, ни личности |

Про склейку у релея — важная честность из `relay_privacy.md` §2.2:
релей **уже сегодня** склеивает псевдонимы получателя через штатный
опрос `acceptedDsts` с одного IP («за неделю наблюдения релей
склеивает всю ленту псевдонимов без единого бита криптоанализа»).
Подписка делает эту склейку явной и долговечной (токен стабильнее
IP), но не создаёт качественно новой утечки — она **расширяет
принятую**. Предлагается записать это в «не обещаем» `relay_privacy.md`
отдельным пунктом (см. §8).

Пуш-токен APNs — идентификатор пары «устройство × приложение»,
выдаёт его Apple; вне APNs он бесполезен (по нему нельзя ни читать,
ни писать, только просить Apple доставить пуш от имени com.chappe.app,
для чего нужен ещё и ключ издателя пушей, §5).

## 2. Отклонённые альтернативы (чтобы не переоткрывать)

| Вариант | Почему нет |
|---|---|
| Фоновое обновление iOS (BGAppRefreshTask) | iOS будит когда сама решит — от 15 минут до часов, без гарантий, отключается в энергосбережении. Для мессенджера не решение; как страховку можно добавить потом отдельной мелкой задачей. |
| Тихий пуш (content-available без алерта) как единственный механизм | APNs «бюджетирует» тихие пуши (единицы в час), роняет их в Low Power Mode и после force-quit. Годится только как довесок к видимому алерту (§3). |
| Расшифровка текста в уведомлении (Notification Service Extension) | Требует выноса состояния рэтчета в App Group и его конкурентной мутации из расширения и приложения — инженерия уровня Signal, месяцы. Кандидат на фазу 2; в v1 уведомление без содержимого — что для приватности даже лучше. |
| VoIP-пуши (PushKit) | Обход правил Apple для не-звонков — бан на ревью. Не рассматривается. |
| Держать TCP-сокет из фона | iOS не даёт; именно поэтому существует APNs. |

## 3. Что летит в пуше

Полезная нагрузка APNs от релея — минимальная и постоянная:

```json
{ "aps": { "alert": { "loc-key": "PUSH_NEW_MESSAGE" },
           "sound": "default",
           "content-available": 1 } }
```

- `loc-key` вместо текста: строка «Новое сообщение» лежит в бандле
  приложения и локализуется на устройстве — через Apple не проходит
  даже готовая фраза, только имя ключа. Ни отправителя, ни чата, ни
  количества в пуше нет **по построению** — нечего утечь.
- `content-available: 1` — просьба заодно разбудить приложение в
  фоне: когда iOS её удовлетворяет, почта забирается ещё до того, как
  человек взял телефон, и «доставлено» у отправителя загорается
  раньше. Это ускоритель без гарантий (после force-quit не работает)
  — корректность на нём не строится.
- `apns-collapse-id` = токен-константа: залп из N кадров схлопывается
  в одно видимое уведомление, а не N подряд (полевой сценарий 15.08:
  «сообщение первое / второе / третье» за минуту).
- Бейдж с числом в v1 не используется: релей не знает непрочитанного
  и знать не должен (см. открытый вопрос §9.4).

**Правило 5 проекта (успех = своё событие) применительно к пушам:**
«APNs принял пуш» ≠ «телефон разбужен» ≠ «доставлено». APNs квитанций
о вручении не даёт. Носителем истины остаётся то же, что сегодня:
кадр забран из ящика (DELETE получателя) и сквозной envelope-ack.
Пуш — ускоритель задержки, не участник контракта доставки; опрос при
открытии приложения никуда не девается и остаётся источником истины.

## 4. Протокол подписки (расширение HTTP-API релея)

### 4.1 Как получатель доказывает право на подписку

Тем же механизмом, что чтение ящика (вариант В, принят 04.08,
`relay_spec_v0.md` №2): суточным box-ключом. Подписаться на пуши
ящика может только тот, кто владеет box-ключом этого dst — тот же
круг, который и так умеет ящик читать. Новых доверий не появляется.

### 4.2 Эндпойнты

```
POST /push/register
  тело: { token: hex64,          — пуш-токен APNs (32 Б)
          env: "prod"|"sandbox", — среда APNs (сборка dev против TestFlight)
          subs: [ { dst: hex16, boxPub: hex64, sig: hex128 }, … ] }
  sig_i = Ed25519(boxKey_i, "rm-push-sub-v1" ‖ nonce ‖ token ‖ dst_i)
  nonce — от челленджа /box/{dst}/challenge любого из dst (один RTT
  на весь пакет подписок, не по числу ящиков).
  Ответ 200: { accepted: N, rejected: [dst…] }.

POST /push/unregister
  тело: { token: hex64 } — стирает токен и все его подписки.
  Авторизация: подпись любым из живых box-ключей токена — либо
  вызов «вслепую» с самого устройства (знание токена = владение
  устройством; токен секретом не является, но и вреда от чужого
  unregister нет — см. ниже).
```

- Идемпотентно: повторная регистрация тех же подписок — 200, строки
  не дублируются.
- Подписка живёт до `expires_at` своей эпохи (+ окно приёма) и
  умирает сама — как ящики. Отдельного «продления» нет: приложение
  перерегистрируется при каждой активации (см. 4.3), это дёшево.
- У каждого повторяемого поля потолок (правило CLAUDE.md):
  `subs` maxItems = 512 за запрос; подписок на токен ≤ 4096;
  токенов на релей — лимит конфига.
- Враждебный `unregister` чужого токена (если токен утёк) — деградация
  до сегодняшнего поведения (нет пушей, опрос при открытии работает),
  не потеря почты. Принято: не строить вокруг этого церемонию.

### 4.3 Пред-регистрация будущих эпох — почему и на сколько

Ящик пары живёт эпоху (суточный псевдоним со сдвигом пары,
`MailboxID.epoch`). Если регистрировать только текущую эпоху,
телефон, не открывавшийся сутки, перестаёт получать пуши — дыра
ровно в том сценарии, ради которого пуши вводятся.

Получатель умеет вычислять свои dst **вперёд** (эпохи выводятся из
pairKey локально). Предложение: при каждой активации приложение
регистрирует по каждой паре dst эпох **[текущая − 2 … текущая + K]**,
K = 7 (открытый вопрос §9.1). Тогда:

- телефон, спавший неделю, всё ещё получает пуши;
- не открывался дольше K дней — пуши гаснут до следующего открытия
  (честный предел, записывается в tester_guide);
- цена: ~50 контактов × 10 эпох = ~500 подписок × ~100 Б ≈ 50 КБ
  одним запросом при активации — копейки.

Утечка пред-регистрации: релей узнаёт псевдонимы получателя **на
K дней вперёд** (сегодня склейка получалась постфактум опросом).
Расширение принятой утечки, фиксируется в §8.

### 4.4 Ящик первого контакта

`FirstContactMailbox` (принятая утечка №3, `relay_privacy.md` §2.6)
подписывается так же — его box-ключ получатель выводит из своего
ключа. Продуктовый выигрыш: **знакомство по QR доходит до спящего
телефона** — новый контакт не остаётся незамеченным на 48 ч.

### 4.5 Отправитель сам себе пуш не шлёт — по построению

dst направленный (`MailboxID.dst(recipientPub, …)` включает ключ
получателя): у каждой стороны пары свой входящий ящик. Отправитель
кладёт в ящик получателя, подписан же на свои — самопуша нет без
всяких исключений в коде.

### 4.6 Что релей хранит и когда стирает

```sql
CREATE TABLE push_tokens (
    token      BLOB PRIMARY KEY,   -- 32 Б APNs-токен
    env        INTEGER NOT NULL,   -- 0 prod / 1 sandbox
    updated_at INTEGER NOT NULL
);
CREATE TABLE push_subs (
    dst        BLOB NOT NULL,      -- 8 Б, как frames.dst
    token      BLOB NOT NULL REFERENCES push_tokens(token) ON DELETE CASCADE,
    expires_at INTEGER NOT NULL,   -- конец окна приёма эпохи dst
    PRIMARY KEY (dst, token)
) WITHOUT ROWID;
```

Стирание: TTL-уборкой тем же фоновым проходом, что кадры и надгробия;
токен без единой живой подписки умирает вместе с последней; ответ
APNs `410 Unregistered` (приложение снесено) — немедленное каскадное
удаление токена. Инвариант тот же, что у ящиков: **лишних метаданных
не копим** — истёкшая подписка не живёт дольше своего dst плюс окно.

### 4.7 Отправка пуша

PUT принят (200, после fsync — контракт `relay_ops.md` WP4.2 не
трогается) → по `push_subs[dst]` найдены токены → пуш каждому,
**асинхронно после ответа отправителю**: судьба пуша не влияет на
код ответа PUT — пуш вне контракта доставки (§3). Ошибки APNs
логируются счётчиком (пульс, правило 3 проекта), в кадрах не
отражаются никак.

## 5. Ключ издателя пушей и деплой

- APNs требует **ключ подписи запросов** — файл `.p8` (ES256) из
  Apple Developer аккаунта владельца (тот же аккаунт, что TestFlight;
  создаётся в разделе Keys одним действием, владелец уже ходил туда
  за ключом ASC API — процедура знакома, `asc_api.py` рядом).
- `.p8` живёт **на релее** в конфиге (как TLS-ключи). Компрометация
  релея по этой части даёт противнику одно: слать мусорные пуши
  пользователям com.chappe.app (раздражение, не содержимое и не
  почта). Отзыв — одним кликом в Developer-аккаунте + новый ключ.
  Записано как принятый риск (§8).
- Среды: dev-сборка по кабелю говорит с **sandbox**-APNs,
  TestFlight/магазин — с **production**. Токен несёт флаг env (§4.2),
  релей держит два HTTP/2-клиента. Классические грабли «пуши не
  приходят на TestFlight» — это перепутанная среда; флаг закрывает.

## 6. Сторона приложения

1. **Entitlement** `aps-environment` + фоновый режим
   `remote-notification` в `UIBackgroundModes` (для content-available).
   Правило Info.plist проекта: проверять в **собранном** plist
   (`plutil -p`), ключи фонового режима — через частичный
   `ios/Chappe/Info.plist`, там уже живёт `bluetooth-central`.
2. **Разрешение человека.** Видимые уведомления требуют системного
   запроса (`UNUserNotificationCenter.requestAuthorization`). Момент —
   не при первом запуске (человек ещё не понимает, зачем), а при
   **включённом релее** после первого успешного знакомства — когда
   польза очевидна. Отказ — честная строка в настройках релея
   («уведомления выключены → сообщения будут ждать открытия
   приложения»), не молчание. Формулировки — `ui_vocabulary.md`.
3. **Регистрация токена**: `registerForRemoteNotifications` при
   активации; токен пришёл/сменился (Apple иногда ротирует) →
   POST /push/register полным пакетом подписок (4.3). Перерегистрация
   при каждой активации — идемпотентна и дёшева.
4. **«Начать заново» стирает пуши.** Урок P0-регресса билда 24
   (26e8941: сброс не стирал новые поля): freshStart обязан
   (а) дёрнуть POST /push/unregister, (б) забыть токен локально,
   (в) снять системные уведомления из центра. Замок — расширение
   `FreshStartCrossTests` (перекрёст «пуши × сброс» — та самая
   клетка матрицы, которую чекап 24 пропустил).
5. **Приём пуша**: видимый алерт трогать не надо (iOS показывает
   сам); фоновый вызов (content-available) → внеочередной опрос
   ящиков — код уже есть (внеочередной опрос при активации,
   028bcd1), вызывается из делегата пуша.
6. Тап по уведомлению → открытие на списке чатов (в v1 без
   маршрутизации в конкретный чат — пуш не знает чата по построению).

## 7. Полевой критерий готовности

Сценарий 15.08 наоборот, оба телефона на TestFlight-сборке:

1. Телефон Б погашен ≥ 5 минут (заморожен наверняка).
2. Телефон А шлёт сообщение через релей.
3. **Ожидание: на Б в течение ~секунд появляется баннер «Новое
   сообщение» без прикосновения к телефону.** Таймкод фиксируется.
4. Тап по баннеру → чат открыт, сообщение на месте, у А —
   «доставлено».
5. Контроль сброса: «Начать заново» на Б → повтор шага 2 → баннер
   НЕ приходит (подписки стёрты), сообщение ждёт в ящике штатно.
6. Дневники обоих телефонов — в git (не в скретч).

## 8. Честные пределы и пополнение «не обещаем»

Дописать в `relay_privacy.md` §5 при реализации:

1. **Токен связывает всё.** Релей видит «эти ящики (включая будущие
   эпохи на K дней) — одно устройство». Расширение утечки №6 (опрос
   и так склеивал псевдонимы); теперь склейка явная и переживает
   смену IP.
2. **Apple видит пульс.** Факт и время каждого пуша (= каждого
   входящего релейного сообщения при живой подписке) видны APNs.
   Содержимое — нет, отправитель — нет, ящик — нет.
3. **Пуши — best effort.** Apple не гарантирует ни доставку, ни
   срок; Low Power Mode, force-quit и «фокусировки» iOS глушат части
   механизма. Контракт доставки на пуши не опирается (§3).
4. **Оффлайн пуши не лечат.** Это ускоритель интернет-пути. Спящий
   телефон в чистом оффлайне будит только LoRa-узел по Bluetooth —
   уже работает, пушей не касается.
5. **`.p8` на релее.** Компрометация релея позволяет слать мусорные
   пуши до отзыва ключа. Почта и содержимое не затронуты.
6. Не открывал приложение дольше K дней → пуши молчат до открытия
   (пред-регистрация исчерпана) — записать в tester_guide.

## 9. Открытые вопросы владельцу

1. **Глубина пред-регистрации K.** Предлагаю **7 эпох (~неделя)**:
   покрывает отпуск выходного дня с запасом; релей знает будущее на
   неделю, не на месяц. Варианты: 3 (меньше утечка, чаще гаснут
   пуши) / 14 (наоборот).
2. **Текст уведомления.** Предлагаю v1 — константа «Новое сообщение»
   (loc-key, §3). Фаза 2 с расшифровкой в расширении — отдельное
   решение, когда дойдём (месяцы, рэтчет в App Group).
3. **Момент запроса разрешения на уведомления** — предложение в §6
   п.2 (после первого знакомства при включённом релее); альтернатива
   — сразу при включении релея.
4. **Бейдж-счётчик на иконке.** Предлагаю НЕ в v1: релей не должен
   считать непрочитанное; локальный бейдж (приложение само ставит
   после фонового забора) — возможен позже без участия релея.
5. **Порядок с держателями раздачи.** Моя рекомендация 15.08 —
   впереди квитанций релеем и SeenMsgIDs: без пушей интернет-путь
   не выглядит живым для нового человека.
